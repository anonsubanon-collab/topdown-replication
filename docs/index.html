TopDown: a feedback-driven multi-agent method for strengthening LLM code judges

An LLM judge reads a program and says whether it is correct. TopDown adds one thing the judge cannot produce on its own: does the program return, on concrete inputs, what the specification says it should? No tests, no reference solution, no execution, no training.

Abstract

Reference-free LLM judges read a generated program and decide whether it meets its intent. They need no tests, reference solution or execution, so they can judge code in any language (we test six languages). Such judges, however, can miss small mistakes. Inspired by top-down perception, our idea is to add evidence that the judge cannot produce from the code alone. TopDown is a training-free method that strengthens existing judges rather than replacing or competing with them. Specification-only agents propose inputs and predict the expected output on each. Code-only agents trace the program on the same inputs. A feedback round re-examines each disagreement, and the surviving disagreements are weighted and added to the judge's own verdict as evidence.

Early results on 1,968 HumanEvalPack programs in six languages and 418 MBPP+ programs with two open judge families. The baselines are the judge alone, self-consistency, multi-agent judging at matched token budgets and MCTS-Judge (the closest execution-free judge to ours). (1) TopDown raises the judge's Kendall's τ by 12–19% on HumanEvalPack and 10–23% on MBPP+, significantly in 11 of 12 comparisons. (2) Multi-agent judging and self-consistency mostly fall short of the judge alone. (3) Against MCTS-Judge, TopDown has higher pairwise accuracy in distinguishing correct from buggy programs for both judges on both benchmarks, and a higher MCC for Qwen-7B (a tie for Llama-8B), using one fifth to one third of its generated tokens.

Why another look at LLM code judges

A judge that reads a program alone has one source of information: its own reading of the code. It can miss small mistakes, and it tends to return a verdict even when it has no grounds for one.

The usual remedies make the model reason more. Self-consistency averages sampled verdicts. Multi-agent judging has several agents trace and debate the program. MCTS-Judge searches over judging steps. In our experiments, once the token budget is matched, neither self-consistency nor multi-agent judging improves on the single judge.

The idea comes from how people review code. Pick a concrete input. Work out from the specification what the output must be. Only then follow the code on that input. Because the expectation is fixed before the code is read, the code cannot change it.

Perceptual decision making works the same way: a top-down expectation meets bottom-up evidence, and the decision accumulates the mismatch. TopDown gives an LLM judge this structure.

RQ1. Does TopDown strengthen the judge at matched compute?

Yes. Kendall's τ rises by 12 to 19% on HumanEvalPack and 10 to 23% on MBPP+, significantly in 11 of 12 comparisons. Multi-agent judging and self-consistency are mostly worse than the judge alone.

RQ2. How does TopDown compare with MCTS-Judge?

It has higher pairwise accuracy in distinguishing correct from buggy programs for both judges on both benchmarks (+0.09 to +0.27) while MCTS-Judge generates 3.3 to 4.7 times more tokens, and it decides better on Qwen-7B, with no significant difference on Llama-8B.

Prior work, and what is different here

Similarity to a reference

BLEU, CodeBLEU, CodeBERTScore, CodeScore and the like score code by its similarity to a reference solution. Similarity is not correctness, and these metrics correlate only weakly with human judgment.

Reference-free judges

ICE-Score and CodeJudge prompt a model to grade a program; MCTS-Judge adds search over judging steps. A single reading of the code is a weak detector of small mistakes.

Generated tests

CodeT and AgentCoder select code by model-written tests, but run the candidate. TRAILS reads input-output pairs that still come from execution. HoarePrompt reasons about spec and code with one model reading both.

Tracing and self-correction

Models can trace code without running it, but about half of their coherent traces still end in a wrong output. Self-correction without an external signal fails, yet a model told where a step went wrong can often repair it.

Closest work: MCTS-Judge

Like TopDown, it predicts expected outputs from the problem statement alone, has the judge simulate the code line by line with the output hidden, and never executes the program. We differ in four places. To our knowledge, no prior work combines these without executing the candidate.

How TopDown works

Six agents, all the same LLM in different roles, in two levels that never see each other's inputs. The specification level says what a correct program should return. The code level says what this program does return. Mismatches get a second look, and the ones that survive are weighed and added to the judge's verdict.

Figure 1. One candidate program through TopDown. Top row: sees only the specification. Bottom row: sees only the code. Each probe input gives one check, an expectation with precision p against an observation with reliability r. Dashed arrows are the feedback round, triggered only by a prediction error.

From checks to a verdict

A prediction error is an observation that differs from its expectation. It triggers the feedback round, up to the re-deriver and down to the re-tracer, and the comparison is repeated. An error that still stands is a confirmed error.

Each check has two probabilities of showing an error. On a correct program an error can only come from a wrong expectation or a wrong reading. On a buggy program the input exposes the bug half the time; otherwise the program behaves as a correct one would.

P(error | correct) = 1 − p·r
P(error | buggy)   = 0.5·(1 − p·(1 − r)) + 0.5·(1 − p·r)
  • Confirmed errors remain: evidence = the sum over them of log P(error | correct) / P(error | buggy). Negative. Agreeing checks add nothing, so a counterexample is not cancelled by inputs that match.
  • No error remains: evidence = the mean over all checks of log (1 − P(error | correct)) / (1 − P(error | buggy)). Positive, at most +0.59 per check.

Score = prior + evidence. Accept if positive. With no evidence, TopDown is the judge alone.

A confident expectation with agreeing tracers counts most; a split expectation with a disputed reading barely counts. All counts (6 probes; 4, 3 and 1 samples) and weights (0.9, 0.6, 0.5) were fixed before the runs and never swept.

Specification

def circular_shift(x, shift):
    """Circular shift the digits of the integer x,
    shift the digits right by shift and return the
    result as a string.
    If shift > number of digits, return digits reversed.
    >>> circular_shift(12, 1)
    "21"
    >>> circular_shift(12, 2)
    "12"
    """

Candidates, as the code tracer sees them

def circular_shift(x, shift):          # correct twin
    s = str(x)
    if shift > len(s):
        return s[::-1]
    else:
        return s[len(s) - shift:] + s[:len(s) - shift]

def circular_shift(x, shift):          # buggy twin
    s = str(x)
    if shift > len(s):
        return s[::-1]
    else:
        return s[:len(s) - shift] + s[len(s) - shift:]

"Is the code correct? YES or NO." Log-odds of the first token: +4.00 for the correct twin, +0.63 for the buggy twin. Both accepted.

The tracers read each program code level

Correct twin: both tracers return the expected value on all six inputs. Six agreeing checks, r = 0.9.

Buggy twin: both tracers return "12" for (12, 1) and "12345" for (12345, 3). The bug joins the two slices in the original order, so the digits never move. The other four inputs happen to give the expected value anyway (full rotations, the reversal branch, a single digit). Two prediction errors, r = 0.9.

The feedback round

Up: the re-deriver is told a check disagreed with "21" for (12, 1), not what the code gave. Its three derivations all say "21"; 7 of 7 agree, p stays 1.0. Same for (12345, 3).

Down: the re-tracer, seeing only the code, again returns "12" and "12345". Three readings agree, r = 0.9. Both errors confirmed.

Evidence and verdict

Correct twin

No error remains. Each check gives log(0.90 / 0.50) = +0.59; the mean is +0.59.

score = 4.00 + 0.59 = +4.59 → CORRECT

Buggy twin

Two confirmed errors, each log(0.10 / 0.50) = −1.61. The four agreeing checks add nothing.

score = 0.63 − 3.22 = −2.59 → BUGGY

When the expectation itself is revised

Python/80, is_happy, buggy twin, same judge. All four predictor samples said False for is_happy("aabb"), both tracers read True. In the feedback round one of the three re-derivations disagreed, so p dropped to 6/7; the re-trace again said True. The error is confirmed but weighs −0.92 instead of −1.61. With a second confirmed error (−1.61) the evidence is −2.53 against a prior of +1.00: rejected.

The baselines, as we ran them

Same model, same specification and code prompts, same one-token verdict as TopDown's judge. Vanilla, self-consistency and multi-agent judging were given at least as many generated tokens per program as TopDown. MCTS-Judge keeps its own settings.

Vanilla judge

One call with specification and code. Score: log P(YES) − log P(NO) from the top-20 log-probabilities of the first token. One generated token. This is also TopDown's prior.

Self-consistency, ×50 or ×30

N step-by-step reviews sampled at temperature 0.7 (up to 1,024 tokens each), each followed by the one-token verdict; the N log-odds are averaged. N = 50 everywhere except Llama on HumanEvalPack (30).

Multi-agent judging, ×4 or ×5

Six agents that all see specification and code: a tracer that picks up to six inputs and traces the program on each (4,096 tokens), an inspector that checks boundary rules (768), three bug-hunting reviewers (768 each, temperature 0.7), and an arbiter that reads all notes and gives the one-token verdict. Run 4 times on HumanEvalPack and 5 on MBPP+, the first greedy and the rest sampled; arbiter log-odds averaged.

MCTS-Judge

No code is released, so we rebuilt it from its paper with the same judge model: tests are written from the specification, the program is simulated on each, and a Monte Carlo tree search over judging subtasks ends in a binary verdict. It keeps the paper's search settings (depth 9, 8 rollouts, 3 simulated tests, 7 simulations each); the judged model writes the tests instead of GPT-4o. Not budget-matched: it generates 3.3 to 4.7 times TopDown's tokens.

RQ1 Does top-down evidence improve the judge at matched compute?

  • Ranking. Over the vanilla judge, τ rises by 11.9 to 18.5% on HumanEvalPack and 9.9 to 22.6% on MBPP+. 11 of the 12 gains over the three baselines are significant; the exception is self-consistency with Qwen-7B on MBPP+.
  • The baselines. At the same budget, multi-agent judging ranks below a single vanilla call in all four settings, self-consistency in three. TopDown's tokens buy new evidence, not repeated opinions.
  • Decisions. Qwen-7B's MCC rises by 17.4 to 50.8% over every baseline on HumanEvalPack, all significant, and on MBPP+ significantly against vanilla and multi-agent. Llama-8B's vanilla judge accepts only 18% of programs although half are correct, and TopDown's evidence mostly counts against programs, so its MCC gains are significant only against multi-agent judging.

What we take from this

  • Why the evidence helps. A judge that reads a program alone has one source of information: its impression of the code. TopDown also asks the judge what the specification demands on a concrete input, traces the program on that input, and compares the two. MCTS-Judge also simulates the code but turns each mismatch into a vote. TopDown weights a mismatch by the model's confidence in its expectation, re-examines a contradiction before considering it a bug and keeps the judge's own verdict in the sum, and it ranks better with between a fifth and a third of the generated tokens (RQ2). Ablations are needed to tell which of these matters.
  • Where it helps and where it does not. TopDown exposes only bugs that a probed input reaches. Decisions also depend on the judge's calibration: Llama-8B's judge accepts few programs, so TopDown improves its ranking but rarely moves a verdict across zero. A better judge would benefit directly, since its prior is left untouched.
  • Limitations. HumanEvalPack builds on HumanEval, which models may have seen in training, and TopDown's first probes are the docstring examples, which a model may also remember. Its bugs are synthetic and usually one line, which favours bug types that change a returned value. The MBPP+ candidates come from one small generator (Qwen2.5-1.5B-Instruct). MCTS-Judge is our reimplementation, as its authors released no code. We report a single run per setting and one prompt per agent, and only function-level programs. A noisy expectation or trace can make TopDown reject a correct program. Closed-source judges and larger models are untested.
  • Next. More benchmarks, larger and closed-source judges to study generalization, agents from a different model family than the judge, component ablations, and a sensitivity analysis over the number of samples per agent.

Reproduce

Scoring needs a CPU and a few minutes and rewrites results/ byte for byte; the bootstrap is seeded.

pip install -r requirements.txt
bash code/score.sh
  • code/topdown_run.py: TopDown's first pass and the baselines (GPU, vLLM). code/topdown_feedback.py: the feedback round. code/mcts_judge_run.py: the MCTS-Judge re-implementation. code/evidence.py: the evidence rule.
  • code/score_paper.py: RQ1. code/score_mcts.py: RQ2. code/make_tables.py: the tables behind Figures 2 and 3.
  • code/run_paper.sh: the exact GPU commands that produced runs/.
  • runs/: verdicts, labels, meta (with a SHA-256 of the verdicts) and transcripts for every run. The example above is Python/65|0 and Python/65|1 in runs/topdown_qwen7b_feedback_hep_transcripts.jsonl.

A GPU rerun gives the same conclusions, not the same verdict files: vLLM sampling is seeded but not bit-reproducible across hardware.
